# Design

## Context

`Responses::stream_reply` 当前建立一次流并交给 `collect_reply`，成功后才提交历史。REPL 已在输出前打印 `Ai › `，并在返回错误时显示原因。见 proposal.md 和本 change 的 spec delta。

## Goals / Non-Goals

**Goals:** 保留原有历史提交边界与流式显示方式，在 Responses 路径内增加最多五次可见重试。

**Non-Goals:** 不改变 Chat Completions，也不增加通用重试框架或配置项。

## Decisions

- 在现有 Responses 方法中循环发起请求，初次尝试之外最多五次。每次使用同一份已完成历史与当前 user 输入构成的请求；只在完整成功后转移响应所有权并提交历史。教程里的简单“失败再试”映射为 Rust 的 `Result` 分支和有界循环，不改动 provider 边界。
- `collect_reply` 仍逐段回调。外层用布尔值记录本次是否已将正文交给终端；输出失败也阻止重试。请求建立、超时、未完成事件或流读取失败若未输出正文，先通过现有回调打印 `retry n/5...` 和换行，再发下一次请求。部分正文后立即返回原错误，防止重复显示。
- 保留每次请求现有的异步 90 秒等待上限；两次尝试之间使用已有 `tokio::time` 短暂等待，避免对短暂故障紧密连续请求。启用现有 SDK 的 `middleware` feature，并给 Responses 客户端设置不带透明重试的传输层，使五次上限对应真实 HTTP 请求。没有增加新 crate；标准库不提供 HTTP 传输，而现有 SDK 已提供所需实现。
- 不采用 SDK 的透明重试中间件，因为它无法覆盖完整的流读取失败，也无法可靠地把每次重试显示在 Ai 输出区。重试消息走现有同步输出回调，避免 provider 直接依赖终端或颜色；Chat Completions 客户端仍保留原行为。

## Risks / Trade-offs

- [永久性错误也触发最多五次请求] → 上限固定，最终错误可见；本次需求未引入错误类型筛选或额外配置。
- [连续超时使一轮等待较长] → 每次保留原有 90 秒上限；每轮最多六次尝试。
- [失败流已在服务端产生响应] → 无法撤销服务端处理；本地仅在完整成功后提交历史。

# Design

## Context

见 proposal.md。当前 `Config::load` 先按工作目录检查 `.env`，再调用会向父目录搜索的 dotenv 接口；默认 SQLite URL 是相对工作目录的常量。`SqlStore::connect` 已会创建 SQLite 文件的父目录。现有 `embed-env` 在编译期嵌入仓库根目录的 `.env`，运行时只补齐尚未设置的环境变量。

## Goals / Non-Goals

**Goals:** 用一个选定的运行时配置目录，同时决定外部 `.env` 的加载位置和默认 SQLite 的绝对地址；让普通 `cargo run` 使用项目根目录配置；保持环境变量、外部文件、内嵌内容的覆盖顺序。

**Non-Goals:** 不改变显式数据库 URL 的语义，不移动旧数据，不改数据库迁移和异步模型请求。

## Decisions

1. 在现有 `config` 模块中用 `std::env::current_exe()` 的父目录定位程序旁边的 `.env`。若该文件不存在，普通构建且可执行文件位于本项目 Cargo target 目录时，再检查编译时记录的项目根目录 `.env`；内嵌构建跳过这一开发便捷入口。其他情况取用户主目录下的 `.geer-agent/`；Unix 使用 `HOME`，Windows 使用 `USERPROFILE`，缺少必要目录时返回可见错误。只加载选中的具体文件，不使用会搜索工作目录和父目录的 dotenv 入口。存在但读取失败的文件不隐式回退，避免误用另一份配置。不引入新 crate，因为标准库足以定位路径，现有 dotenv 依赖已负责解析。
2. 将选定目录作为 `PathBuf` 在 `Config::load` 中持有，并传给现有数据库配置解析。只有默认 SQLite 地址由该目录下 `.db/geer.sqlite` 生成绝对 URL，生成时转义路径里的 URL 特殊字符；用户显式提供的 URL 保持原样，远程数据库不受目录影响。沿用现有 DAO 在连接前创建目录，不再另写一套目录创建逻辑。运行时没有外部文件时仍选用户目录，这样仅用进程环境或内嵌配置运行时也有稳定的数据位置。
3. 这对应教程中的“启动时读取配置”，Rust 中由拥有路径的配置加载步骤完成，借用目录给数据库解析即可；错误通过 `Result` 向启动入口传播。目录选择和配置解析是同步操作，现有异步数据库连接、流式模型输出及 REPL 不需更改。测试用复制到临时目录的真实二进制验证位置，而非修改测试进程的全局工作目录。

## Risks / Trade-offs

- [旧工作目录中的默认数据库不会自动出现] → 文档说明旧文件可通过显式 URL 继续使用，不自动搬迁。
- [用户目录或程序目录不可写] → 保留现有数据库连接告警；不会改写到另一个目录。
- [Windows 与 Unix 主目录环境变量不同] → 按平台取对应变量，并在子进程测试中使用独立的临时主目录。

## Migration Plan

更新 README 和示例配置：普通 `cargo run` 可继续使用项目根目录的 `.env`，独立产物可将其放在可执行文件旁或用户目录。需要继续使用旧 `./.db/geer.sqlite` 时显式设置对应 SQLite URL。撤销本次代码可恢复旧的工作目录行为，数据库文件本身保持不变。

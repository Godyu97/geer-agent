# Design

## Context

现有 provider 的 Chat Completions 与 Responses 分支各自保存历史并流式显示文本；前者读取文本 delta，后者以完成事件提交完整输出。两者都已有函数工具的 SDK 类型。

## Goals / Non-Goals

**Goals:** 在现有分支上增量加入相同的工具节奏，不改变 REPL 的普通聊天入口和模型配置。

**Non-Goals:** 不建通用 Agent 框架，不在本次加入本地危险能力。

## Decisions

- 共享一份轻量工具定义、参数校验和执行入口；两个协议分支分别把调用映射到各自的消息格式。这样避免抽象掉两种流事件的关键差异，也不复制工具行为。
- Chat Completions 按调用 `index` 聚合流式 `id/name/arguments`；缺少 id 时生成本轮唯一值。Responses 在完成事件的输出中读取函数调用，用原 `call_id` 配对结果。只有完整调用才执行；工具参数片段也刷新流空闲计时。
- 每次用户输入先构造临时历史；完成的工具调用及结果成对提交。若后续模型请求失败，保留已执行部分；若尚无工具执行，沿用原有回滚。工具返回 `Result`，可恢复错误转为结果文本供模型自检，协议不完整则直接报错。
- `GEER_AGENT_TOOLS=off` 从请求中移除工具清单，并让执行入口拒绝调用。`get_current_time` 返回系统本地时区的可读时间。增加直接依赖 `serde_json` 处理模型 JSON 参数；增加 `chrono` 获取并格式化本地日期时间，因为标准库只有系统时间戳，没有本地日历格式化。

## Risks / Trade-offs

- [兼容网关不支持工具协议] → 保留其请求错误，不静默切换接口。
- [流式片段不完整] → 不执行未完成的调用，报告协议错误。
- [工具轮次无限增长] → 每条用户输入最多五轮工具调用。

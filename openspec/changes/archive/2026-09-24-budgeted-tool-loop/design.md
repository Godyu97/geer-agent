# Design

## Context

见 `proposal.md` 的 Why。当前 `agent` 用一个常量和 `for` 循环限制工具轮次：每次模型响应若含调用就顺序执行整个批次，第六次模型仍请求工具时直接显示停止提示，并且不再请求总结。`Prompt` 已经统一拥有 Chat Completions 与 Responses 的系统上下文和对话历史；`provider` 每次只完成一个模型步骤，传入空工具清单时两种协议都不会声明工具。这些现有边界足以增量加入预算状态和无工具 Finalization，不需要重写 provider 或 tools。

当前主规格目录尚未包含 `tool-loop`，其基线契约仍位于已完成但未归档的同名 change 中。本 change 的 MODIFIED requirement 以那份完整契约为基线；实现不受影响，但归档本 change 前必须先同步或归档基线 change，避免修改目标在主规格中不存在。

## Goals / Non-Goals

**Goals:**

- 每条用户输入创建独立、可测试的 Turn 与 Tool Call 预算状态。
- 让预算提示只影响当前模型请求，不污染长期对话历史。
- 在硬预算内保留一次无工具回答机会，并保持两种模型协议行为一致。
- 沿用已有工具执行、授权、消息提交与错误回滚路径。

**Non-Goals:**

- 不抽象通用 Workflow Runtime，也不为尚未实现的 Subagent 预建层级预算。
- 不改变工具的同步批次语义，不在本次推断工具依赖或并行安全性。
- 不把字符串工具结果改造成结构化成功/失败类型；连续错误与进度检测留给后续 change。
- 不持久化或上报指标，也不让用户配置预算数值。

## Decisions

### 1. 在 `agent` 内增加最小预算状态

增加仅由一次 `handle_message` 持有的 `AgentBudget`、`AgentMetrics` 和轻量运行状态。默认预算为 `soft_turn_limit = 12`、`max_turns = 30`、`max_tool_calls = 100`；指标只包含本阶段真正用于决策的 `turns` 与 `tool_calls`。每条用户输入重新创建状态，因此 `/reset` 无需额外清预算，也不会让上一轮消耗影响下一轮。

不只把旧常量从 5 改成 30：那样仍无法区分一个响应内的多个调用、无法在耗尽前提示模型，也无法优雅收敛。也不把预算放进 `Config`：当前默认值是运行时安全策略而非用户功能，过早开放环境变量会增加无关校验面。

### 2. 明确定义计数点和循环顺序

一次成功取得的 Assistant 响应将 `turns` 加一；无论该响应包含零个、一个还是多个工具调用，都只增加一个 Turn。`tool_calls` 只在完整批次即将实际执行时按调用数量增加，未执行的调用不计数。

循环按以下顺序工作：

1. 根据已用预算生成当前请求的临时提示；若只剩最后一个 Turn 或 Tool Call 预算已经耗尽，直接进入 Finalization。
2. 用现有工具清单请求一个模型步骤，并在成功返回后增加 Turn。
3. 没有工具调用时沿用 `finish_turn`，自然结束。
4. 有工具调用时先检查整个批次是否能放入剩余 Tool Call 预算；可以则计数、按现有顺序执行并应用完整调用/结果对，不可以则一个也不执行并进入 Finalization。
5. 应用结果后重新检查预算并继续循环。

整批接受或整批拒绝可以避免同一 Assistant 响应只返回部分工具结果，也让 Chat 的 `tool_call_id` 配对和 Responses 的完整输出保持合法。执行并行化需要工具副作用元数据，留给后续阶段。

### 3. 把第 30 个总 Turn 保留给必要的 Finalization

`max_turns` 统计所有模型 Assistant 响应，包括 Finalization，而不是允许硬上限后出现未计费的第 31 次调用。当已经完成 29 个 Turn 且仍未结束时，第 30 次请求使用空工具清单和专用收敛指令；若更早耗尽 Tool Call 预算，也在当时的剩余 Turn 内立即执行同一路径。

这会让工具可用的模型步骤最多为 29 个，但保证“最多 30 个 Assistant 响应”是真实硬边界。相比先允许第 30 次继续请求工具、再额外调用一次模型，这一选择更容易解释、测试和控制成本。

### 4. 预算提示是请求快照的一部分，不进入历史

为 `Prompt` 的消息快照增加可选运行时指令：Chat Completions 将静态指令合入首条 system 内容，Responses 将其合入 `instructions`。基础系统上下文、用户/助手历史和 pending 工具对仍由 `Prompt` 原样拥有；预算提示不写入历史，因此后续用户轮次不会看到已经过期的“剩余 3 Turn”。

完成第 12 个 Turn 后使用通用收敛提示；剩余不多于三个 Turn 时写明准确余量；只剩一个 Turn 时改用 Finalization 指令。提示全部是程序内静态文本，不拼接用户输入或工具结果，避免把低信任内容提升为 system 指令。

不把提示作为普通 user 消息：那会污染会话语义，并可能在 `/reset` 前一直留存。也不只在终端打印提醒，因为预算的主要作用是改变模型下一步决策。

### 5. Finalization 从协议层关闭工具并提供本地兜底

Finalization 调用现有单步 provider，但传入空工具清单；两种协议因此都不会发送工具定义。专用指令要求模型仅用已有上下文给出最佳回答，并明确未完成或未验证项。成功返回纯文本时仍通过 `Prompt::finish_turn` 保存，用户可在下一轮继续。

若一个普通步骤提出的批次超出 Tool Call 预算，该未执行的 Assistant 工具调用不写入 `Prompt`，避免产生没有结果配对的悬空消息；Finalization 指令会说明有调用因预算未执行。若 Finalization 请求失败，或兼容接口在未声明工具时仍返回调用而没有有效文本，Runtime 不执行调用，也不把悬空调用写入历史，而是提交此前完整的调用/结果对并显示固定的预算耗尽与未完成提示。

正常模型请求的错误规则保持不变：尚未执行工具时回滚本轮用户消息，已有工具结果时提交完整历史再返回错误。流式文本和 `on_delta` 的 I/O 错误继续沿用现有异步传播方式；Finalization 文本也使用同一流式回调。

### 6. Rust 映射与依赖边界保持简单

教程中的 Budget Controller 在本阶段映射为 `agent` 栈上的拥有型状态，而不是全局变量或 trait 框架；循环按顺序可变借用状态、`Prompt`、provider 与 `Tools`，每个 `.await` 前完成计数判断，不产生跨任务共享所有权。`provider` 仍只负责异步协议请求和流解析，`tools` 仍不引用 provider，`Prompt` 只负责生成协议保真的消息快照。

所有计数、比较和静态提示都由标准库完成；现有依赖已经支持两种协议的空工具请求，因此不新增 crate。环境配置、API key 失败路径、请求重试和流式空闲超时均不改变。

## Risks / Trade-offs

- [Turn 边界出现 off-by-one，导致只有 29 个总响应或意外发出第 31 个请求] → 用 11/12、27/28/29/30 和自然结束边界的表驱动单元测试固定计数语义。
- [模型忽略软提示继续探索] → 软提示只负责引导；30 Turn 与 100 Tool Call 仍由 Runtime 强制执行。
- [超预算批次中可能有本可执行的前几个只读调用] → 为协议完整性整批拒绝；部分执行与安全并行留给有调度元数据的后续 change。
- [Finalization 接口仍返回工具调用或请求失败] → 不执行、不保存悬空调用，并输出确定性的本地降级提示。
- [临时提示改变模型系统上下文] → 仅追加短小静态指令并用请求体测试确认提示不进入持久历史。
- [未归档的 `tool-loop` 基线使 delta 无法直接归档] → 实现阶段沿用现有代码契约；归档阶段先同步或归档基线 change，再校验本 change。

## Migration Plan

这是进程内行为升级，没有磁盘数据迁移。先引入预算状态与边界单元测试，再让 `Prompt` 支持临时指令，最后接入 Finalization 并更新两种协议的集成测试；每一步保持普通文本回答和一轮工具调用可运行。若回归失败，可回退本 change 的循环和临时提示改动，恢复当前五轮行为，不影响配置或已保存数据。
